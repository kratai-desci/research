# E13: a practice ground for learning a specialised tool

*Copied from the experiment's working page on 17 Nov 2026. Charts that were drawn live from data are given as tables of that data.*

Status: building, 12 Nov 2026.

**Scope.** E13 builds the practice ground and checks it: about 800 practice questions on BFCL's own tools, with hidden reference solutions, validated against frozen models whose BFCL scores we know. **E14** designs the agent that learns on the job and runs the learning arms on this ground. The sections below record the whole plan agreed so far, so E14 can start from it.

## The story

A new hire joins a small office that runs its own software. Colleagues hand over everyday requests, with no answer sheet. The hire tries, hits errors, learns the quirks of the tools, and after a probation period works alone with confidence.

discuE13 tests whether a small model can do the same: become a **specialist in one set of tools by learning on the job**, with no oracle. The goal is a specialist, not a model that is good at every kind of tool use.

| Office | E13 |
| --- | --- |
| New hire | Qwen3-1.7B, plain |
| The office's software | BFCL's 8 multi-turn tool sets, run in BFCL's own open-source simulators |
| Everyday requests, no answer sheet | About 800 practice requests written by a bigger AI (questions only, as far as the agent is concerned) |
| Learning from mistakes | The agent learns from each step's real tool feedback |
| Working alone after probation | Frozen, then the official BFCL exam |

## Why this follows from E11 and E12

- E11: our BFCL setup reproduces the published numbers for Qwen3-0.6B and 1.7B. Plain Qwen3-1.7B scores about 84 non-live, 74 live and **16 multi-turn**.
- E12: labelled training on ToolRL's data did not make a modern small model a better tool user on the official exam. The paper's big jump came mostly from learning its answer layout (the wrapper): about +45 on its own exam, about 0 on the official one.
- What is left to improve is **tool skill itself**, mainly multi-turn: tracking state, reading results, recovering from errors. That is what E13 targets.

## Agreed design decisions

1. **The wrapper is fixed.** Every arm uses BFCL's official Qwen3-FC handler, the model's native tool layout, as on the leaderboard. Nothing is trained on the layout, so any gain comes from tool skill.
2. **Practice ground: BFCL's own tool simulators** (Apache-2.0). Training on the exam's tools is allowed; training on its questions is not. The paper reports this as in-domain practice: same tools, new tasks.
3. **Practice tasks: written by a bigger AI.** It sees only the tool descriptions, never the 800 exam questions. No near-duplicate filter: overlap can only be by chance, and the paper says so.
4. **No oracle for the agent.** It never sees answers or scores. It learns only from what a real deployment would give it: the tools' replies, including errors, and its own expectations.
5. **Learning by doing, not by watching.** Watching a person do the task would be a demonstration, which counts as a label. That could be a later comparison arm.
6. **A hidden grader, for measuring only.** With each practice question, the bigger AI also writes a hidden reference solution. We run it in the simulator and compare final states, as BFCL scores multi-turn. Tasks whose reference fails to run are dropped. Scores go to a separate log that the learning process cannot read.
7. **The exam: the full official BFCL v4,** frozen, without web search, as in E11. It gives overall plus every group, and doubles as the forgetting check.
8. **Learning during the exam** is a secondary mode. The agent takes the 800 multi-turn questions once in order, learns between them without answers, and each is scored on its first attempt. It can only improve multi-turn (and partly memory), because only there do tools run. Its curve is plotted against the frozen model on the same order, over 3 orders. BFCL's 4 multi-turn groups are variants of the same 200 scenarios, so results are also reported by first versus repeated scenario.

## Measuring progress

- **Growth curve on the real yardstick:** every \~200 practice tasks, freeze a copy and run the BFCL multi-turn exam. The copy never learns from it.
- **Hidden practice score:** the share of practice tasks solved, from the hidden grader, never shown to the agent.
- **Free signals:** tool errors per task, steps per task, and how well the agent predicts tool replies.
- **Confidence:** BFCL's missing-function and missing-parameter groups test whether the agent knows when it cannot do a task and asks instead of guessing.

## Comparisons

- **Main:** the same agent learning versus frozen, from the same start. That is the core claim.
- **Context:** frozen models on the same exam and scorer: plain Qwen3-1.7B (about 16 multi-turn, 30 overall), xLAM-2-1B (35 multi-turn) and xLAM-2-3B (58), trained with labelled multi-turn data.
- **Labelled baseline, needed before publishing:** a working labelled-training arm in the same setting (native format, official exam), for example a short SFT, then GRPO. E12's GRPO replication did not learn ToolRL's format, so it cannot serve as this baseline.

## What the paper will say

- A bigger AI wrote the practice questions and hidden reference solutions. These were used only to measure progress; the agent never saw answers or scores.
- Practice used BFCL's own tool simulators with new tasks: in-domain practice, not training on exam questions.
- E12's GRPO replication did not learn ToolRL's format; its numbers are not a fair test of that paper's GRPO claim.

## E13: build and validate the practice ground

Before any learning, check that the practice questions and the hidden grader measure the same skill as BFCL.

1. **Write the practice set:** the bigger AI writes about 800 questions with hidden reference solutions, from the tool descriptions only. Keep those whose reference runs without errors.
2. **Validate with frozen models from E11 and E12:** run Qwen3-0.6B, Qwen3-1.7B, xLAM-2-1B and xLAM-2-3B on the practice set with the hidden grader, no learning.
3. **Pass if** the practice scores rank the models the same way as their BFCL multi-turn scores (0.6B about 4, 1.7B about 16, xLAM-1B about 35, xLAM-3B about 58), and the levels are in the same range. If the practice set is far easier or harder, or ranks them differently, fix the questions or the grader before going on.
4. **Then build the agent** and run the learning arms.

### How it is built (12 Nov 2026)

- **Writer:** Gemini 3 Flash on Vertex AI, the only Gemini model this GCP project can call (the Pro models are refused). It sees each tool set's function descriptions and simulator source, a random user theme, and its own recent tasks for the same tools, so it varies them. Tool sets are drawn one third single, two thirds pairs, as in BFCL's base group.
- **Checking each task:** its reference is run turn by turn in BFCL's simulators. A task is kept only if every call runs without an error. On a failure the writer sees the error and what the calls returned, and gets 2 tries to fix it.
- **Format:** BFCL's own question and answer files, so the official handlers, simulators and scorer run unchanged (lab/e13/practice.py, lab/e13/practice\_bfcl.py).
- **Smoke test:** 4 of 5 tasks kept. bfcl ran Qwen3-0.6B on them and scored them end to end.

### Validation targets

The practice set is like BFCL's base multi-turn group, so each model's **base** score is the target:

| Model | BFCL multi-turn base (ours, E11/E12) | Practice set |
| --- | --- | --- |
| Qwen3-0.6B | 7.0 | running |
| Qwen3-1.7B | 20.0 | running |
| xLAM-2-1B | 44.5 | running |
| xLAM-2-3B | 70.5 | running |

### Version 1 failed validation (12 Nov 2026)

800 tasks kept, 36 dropped. The xLAM models ranked as on BFCL but scored far lower:

| Model | Practice v1 | Practice v1, final state only | BFCL base, final state only | BFCL base (official) |
| --- | --- | --- | --- | --- |
| xLAM-2-1B | 8.4 | 32.3 | 52.0 | 44.5 |
| xLAM-2-3B | 21.0 | 49.4 | 74.5 | 70.5 |

- **Main cause: needless calls in the references.** BFCL also checks that the model's tool results include every result the reference got. Gemini's references often had lookups the task did not need (for example a stock symbol lookup when the user named the company), so a model that skipped them failed. Scoring by final state alone shows this explains most of the gap (8.4 to 32.3).
- **The rest: harder or ambiguous requests,** for example whether hashtags go in a post's tags or its text.
- Version 1 stays in the bucket (e13/practice, bfcl/e13) for the record.

### Version 2 (running)

- The writer is told to use the **fewest calls**: a read-only call only when the user asks to see that information or the task cannot be done without it.
- Every deciding value is stated in the request (exact texts, amounts, which field).
- Each task gets **one strict review** by the writer against these rules, then its reference is run again.
- Same validation: the four frozen models on the new set (bucket e13/practice-v2, bfcl/e13v2).

### Version 2 results (12 Nov 2026)

| Model | BFCL base | Practice v1 | Practice v2 |
| --- | --- | --- | --- |
| xLAM-2-3B | 70.5 | 21.0 | 29.0 |
| xLAM-2-1B | 44.5 | 8.4 | 16.3 |
| Qwen3-1.7B | 20.0 | 14.3 | 18.9 |
| Qwen3-0.6B | 7.0 | 1.6 | 1.1 |

Qwen3-1.7B matched its BFCL level, but xLAM stayed at about 40% and dropped below Qwen3-1.7B. Compared with BFCL base, v2's turns asked for too much: 2.3 calls per turn against 1.6, and only 23% of turns needed a single call against 65%. Most failures came in the first, most packed turn. Some lookups could be skipped by guessing (user ids like USR001, well-known ticker symbols), and some requests hinged on a tool's answer ("if the tire pressure is low, find a shop").

### Version 3 (running)

- **BFCL's shape:** turns per task and calls per turn are drawn from BFCL base's own counts (statistics only), and a task that goes over its plan is fixed or dropped.
- **No requests that hinge on a tool's answer.**
- **Solver check:** Gemini works each task through the simulators without seeing the reference, and BFCL's own multi-turn checker must pass it. A task that fails gets one fix, then is dropped. This catches ambiguity, guessable shortcuts and needless calls together, much as BFCL's questions were checked by people.
- Written on a CPU VM (L4 GPUs were out of stock); the four validation exams wait for it (bucket e13/practice-v3, bfcl/e13v3).

### Version 3 results (12 Nov 2026)

| Model | BFCL base | v1 | v2 | v3 |
| --- | --- | --- | --- | --- |
| xLAM-2-3B | 70.5 | 21.0 | 29.0 | 71.8 |
| xLAM-2-1B | 44.5 | 8.4 | 16.3 | 55.4 |
| Qwen3-1.7B | 20.0 | 14.3 | 18.9 | 56.1 |
| Qwen3-0.6B | 7.0 | 1.6 | 1.1 | 27.6 |

xLAM now matches BFCL, and each family ranks as on BFCL, but Qwen3 scores 3 to 4 times its BFCL level and Qwen3-1.7B ties xLAM-2-1B. Likely reason (not yet checked): v3 spells out every step, while BFCL's questions leave the obvious steps (changing folder, looking up an id, logging in) to the model. xLAM was trained on BFCL-style tasks and handles those; Qwen3 follows explicit instructions well. So v3 measures tool use when told clearly, and BFCL also measures working out what was not said.

### Version 4 (running)

As v3, with requests in BFCL's style: the goal and every value that decides the result, but not the steps a competent assistant can work out (moving into the right folder, looking up an id for a named person or company, logging in with credentials given earlier, a prerequisite the tools require, reusing an id an earlier turn produced). The outcome stays unambiguous, and the solver check still applies. Implicit is not ambiguous: only the route is left open, never the result. Bucket e13/practice-v4 and bfcl/e13v4; all versions stay saved and usable.

## E14 (next): design of the agent

Open questions for the next discussion:

- How the agent learns from each step: notes it writes and reads back (no weight changes), weight updates from predicting tool replies (ECHO-style), or both.
- What it does after an error: retry policy, and what it keeps from the episode.
- How memory and weight updates avoid forgetting the rest of BFCL.
- Compute: the multi-turn exam takes 4 to 15 h per model on an L4, so development runs will use a subset.
